# MARC → BIBFRAME coverage

This document is a **static** view of what the LoC `marc2bibframe2`
XSLT extracts from each MARC source field. It is auto-generated by
parsing the vendored stylesheet under
`third_party/marc2bibframe2/xsl/`. A row appearing here only means the
XSLT contains code to handle the field — it does **not** mean that the
field actually occurred in any corpus we have processed.

The doc has four auto-generated sections, regenerated together by
`bffi-pipeline regenerate-marc-to-bibframe-mapping` (use `--check` in
CI to guard against drift):

1. **Coverage matrix** — per-MARC-tag input coverage: modes, indicators
   tested, subfields read, controlfield/leader position reads, BIBFRAME
   classes/predicates emitted.
2. **Dynamic constructor appendix** — every template that builds an
   output element via `<xsl:element name="{$var}">`. These can't be
   resolved statically; affected tags carry a partial-coverage note.
3. **Round-trip cross-check** — comparison against the reverse
   converter's `MARC_EMIT_REGISTRY` (the source of
   `docs/bffi_to_marc_mapping.md`). Per tag verdict: round-trippable,
   forward-only, reverse-only, or asymmetric.
4. **Generator metadata** — XSLT commit SHA, module/template/tag
   counts, cross-check tally.

## Reading the tables

- **Indicator cells**: an `ind1=` or `ind2=` entry means the XSLT
  template has at least one `xsl:when test="@ind1='X'"`-style literal
  branch for that value. The literal MARC blank indicator (a space) is
  rendered as `#`. `_(projected, no literal tests)_` means the
  template references the indicator (e.g. `<xsl:value-of
  select="@ind1"/>`) but doesn't branch on a literal — the analyzer
  can't enumerate which values get through.
- **Position-read cells**: written `008/35-37` etc., MARC convention
  (0-based, inclusive end). The XSLT uses 1-based `substring(., N, M)`
  internally; this doc translates.
- **BIBFRAME-emitted cells**: literal element constructors
  (`<bf:title>`) and resolvable `<xsl:element name="bf:Foo"/>` are
  listed verbatim. Dynamic constructors appear as
  `<dynamic:{$varName}>` and trigger a per-tag note + an entry in the
  dynamic-constructor appendix.
- **880 (alt-script) folding**: marc2bibframe2 routes 880 via a `$6`
  prefix dispatch back to the linked tag's template. Affected tags
  carry an "also handled via 880 `$6` dispatch" note; 880 does not
  appear as its own row unless the XSLT has a stand-alone 880 handler
  with no dispatch linkage.

## Known limitations

1. **Static, not empirical.** A row here means the XSLT contains
   handling, not that any record exercised it. The
   `bffi-pipeline diagnose-marc-coverage` command provides the
   empirical (corpus-derived) view.
2. **Dynamic `xsl:element` constructors are irreducible.** Templates
   that build output element names from XSLT variables (e.g.
   `<xsl:element name="{$vTitleClass}"/>`) can't be resolved without
   running the stylesheet. Affected tags carry a "partial coverage"
   note and the appendix lists each site.
3. **Mode aggregation collapses per-mode detail.** A tag handled in
   multiple modes (`work`, `instance`, `adminmetadata`, …) is one row
   with a `Modes` cell listing all modes. The per-mode subfield /
   output breakdown is not surfaced.
4. **Indicator projection is opaque.** When a template references
   `@ind1` / `@ind2` without a literal-equality test, the analyzer can
   tell *that* the indicator was read but not *which values* the
   template would fire for in practice.
5. **The cross-check compares MARC tags, subfields, and indicators
   only.** It does not compare the BIBFRAME terms emitted by the
   forward path against the BFFI terms read by the reverse path — that
   pairing is the BIBFRAME ↔ BFFI mapping doc's job
   (`docs/bf_to_bffi_mapping.md`).
6. **`reverse_only` is not automatically a bug.** Some MARC tags are
   reconstructed by the reverse converter from BFFI provenance
   metadata that has no forward-path equivalent — they will always be
   `reverse_only`. A `forward_only` verdict is what flags
   reverse-converter work; an `asymmetric` verdict warrants per-tag
   review.
7. **Submodule SHA churn.** Every regenerated doc embeds the
   marc2bibframe2 submodule's HEAD SHA. A submodule bump that doesn't
   touch the parsed bits still bumps the SHA, producing a small diff
   that must be regenerated and committed.

## Round-trip cross-check vs `bffi-to-marc`

Compares each MARC tag the marc2bibframe2 XSLT reads against each MARC
tag the BFFI → MARC reverse converter emits. Rows are grouped by
verdict; within each group, controlfields come first, then `leader`,
then datafields, alphabetical inside each.

Verdict legend:

- **✓ round-trippable**: both directions touch the tag and their
  subfield / indicator sets match.
- **≠ asymmetric**: both directions touch the tag, but the
  subfield-codes or indicator-values they read/emit differ.
- **→ forward only**: marc2bibframe2 reads the tag; the reverse
  converter never emits it. This is the "forward → reverse data loss"
  case — work to do on the reverse side.
- **← reverse only**: the reverse converter emits the tag;
  marc2bibframe2 doesn't read it. Often by design (reverse rebuilds
  from BFFI provenance metadata), occasionally suspicious.
